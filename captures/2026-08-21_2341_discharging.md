## What the pairing refutes

**`Yavb[1]` is not the BMS flag word.** Byte-identical `1001100000000000` in both
captures while the BMS currents swapped ends entirely (29.6 / 0 became 0 / 27.3). It also
carries three set bits against four affirmative portal flags — Allow Charging, Allow
Discharge, Communication Control Function, Communication Normal — so one-digit-per-flag
does not survive arithmetic, whatever the assignment. And it is not a per-cell mask: it
held while the max and min cell positions moved 9→13 and 17→29. Twelve sensors were
recorded against this candidate; all twelve are back to having no decode path.

**`eo8w[1]` is not the light-status word.** Byte-identical `B010000000000` while Charging
Light Status went Flicker → Off.

**`noeP[3]` is not `total_number_of_grid_connection`.** It moved `2` → `0` while the
portal held at 2 throughout. It tracks PV2 activity. This needs no further capture — an
earlier note asking for a single-inverter capture to settle it is obsolete.

**The BMS permission flags will never move with battery state.** *Allow Charging* and
*Allow Discharge* both read `Yes` in both captures. They are permissions the pack grants,
not a description of what it is currently doing, so no charge/discharge pairing can
decode them.

## What the pairing suggests but cannot prove

`eo8w[2]`, the 21-character blob, is the only place the light statuses can still live:

```
charging     20211002120B117020000
discharging  20211002100B127000000
                      ^   ^  ^
positions             9  13  16      2→0,  1→2,  2→0
```

Exactly two portal fields in that family changed — Charging Light Status Flicker → Off,
and Charging Main Switch Open → Close. **Three positions moved and two fields changed**,
so no position can be uniquely assigned. The digits observed are 0, 1, 2 and 7, which is
consistent with an enum where 0 = Off and 2 = Flicker, but two positions made the same
2 → 0 transition, so even under that reading the charging light could be either.

Nothing is published from this. A third capture in a state that moves one of these fields
alone would separate them.

## Still open after this capture

The `INVERTER_COUNT` scaling. The portal reports `Output Active Power 0.641 kW` and the
bridge publishes `c_load_w = 1282`, exactly twice. At this instant PV is 0 and the grid is
disconnected, so the battery is the only source and the balance is clean: 1282 / 1431 =
89.6% conversion efficiency under the bridge's reading, against 44.8% if the portal figure
were already the system total. 89.6% is what an inverter does; 44.8% is not.

That is an engineering judgement about idle losses, not arithmetic, and it does **not**
settle the question. The charging capture cannot help: this unit's own PV is not the
system's, so the twin's array is a free parameter that absorbs any discrepancy. The
question reduces to one nameplate — if a single inverter is rated 11 kW then `2l0E`
carries per-unit figures and `c_load_w` is right; if 11 kW is the pair's rating then every
scaled `c_*` power is double. **A photograph of one inverter's rating plate settles it in
a minute.** Failing that, a clamp meter on the AC output against `c_load_w`.
